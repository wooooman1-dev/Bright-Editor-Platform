# 콘텐츠 포맷 다양화 설계 문서 (Content Format Diversity Spec)

> Bright Editor Platform / Prompt Engine 하위 기능 설계
> 상태: 설계 초안 (구현 전, 승인 대기)
> 관련 원칙: Design First — 이 문서 검토 및 승인 후에 구현 착수

---

## 1. 문제 정의

현재 AI 생성 글이 다음과 같은 고정 구조를 매번 동일하게 반복하고 있음 (실제 발행글 2건 분석 기준):

- 도입부 화법: "OOO의 핵심은 ~에 있습니다" 패턴 고정
- 소제목 문형: "OOO 방법: 무엇 무엇" 패턴 고정
- 본문 구성요소: 표 → 단계형 리스트 → 가상 사례 → 비교표 → 체크리스트 → 마무리 요약, 매 글 동일 순서로 전부 포함

**리스크**
- AdSense 심사 시 "템플릿 티" → 콘텐츠 다양성 부족으로 판단될 가능성
- SEO 관점에서도 검색엔진이 사이트 전체를 낮은 다양성 콘텐츠로 인식할 가능성
- 장기적으로 브랜드 톤이 단조로워짐

**목표**
동일한 "Hybrid AI Editor" 1회 생성 구조(Writer+SEO+ImageStrategy+InternalLink+AdStrategy+Editor를 한 번에 수행)는 유지하되, 결과물의 **표면적 구조·화법·구성요소 조합**에 다양성을 강제하는 계층을 Prompt Engine에 추가.

---

## 2. 설계 원칙

- 비용 효율성 원칙 준수: 다양성 확보를 위해 추가 AI 호출을 만들지 않는다. 기존 1회 생성 호출의 **프롬프트 입력값**을 다양화하는 방식으로 해결한다.
- Agent Ready 원칙 준수: 이 로직은 향후 별도 "Structure Planner Agent"로 분리 가능하도록, 독립 모듈(포맷 선택기)로 설계한다.
- Core에 위치: 플랫폼 전체(Tistory, Blog, YouTube 등)에서 재사용 가능해야 하므로 `Core > Prompt Engine` 하위에 위치.

---

## 3. 구성요소 설계

### 3.1 포맷 프리셋 정의 (Format Presets)

콘텐츠 포맷을 5종으로 정의하고, 각 프리셋은 아래 속성을 가진다:

| 포맷 ID | 이름 | 핵심 뼈대 | 적합한 주제 유형 |
|---|---|---|---|
| `guide` | 정보 가이드형 | 조건/기준 분리 → 단계별 절차 → 체크리스트 | 절차·방법 설명 (현재 기본값) |
| `compare` | 비교형 | 대상 A/B 특성 나열 → 비교표 → 상황별 추천 | 상품/선택지 비교 |
| `faq` | Q&A형 | 질문 목록 → 개별 답변 → 종합 정리 | 흔한 질문이 많은 주제 |
| `scenario` | 사례 중심형 | 가상 인물 시나리오를 글 전체 뼈대로 전개 | 의사결정 과정이 중요한 주제 |
| `mythbust` | 오해 바로잡기형 | 흔한 오해 나열 → 각각 정정 → 올바른 정보 정리 | 오해가 많은 주제 |

각 프리셋은 다음 하위 속성을 프롬프트 변수로 가진다:
- `intro_style`: 도입부 화법 3~4종 (예: 질문 던지기형 / 상황 제시형 / 핵심 요약 선제시형)
- `heading_pattern`: 소제목 문형 규칙
- `optional_blocks`: 표, 체크리스트, 가상 사례, 비교표 등 "선택적으로 사용 가능한" 구성요소 풀 (전부 강제 사용 금지)

### 3.2 포맷 선택 로직 (Format Selector)

입력: 주제/카테고리, 최근 N개 발행 글의 메타데이터(포맷 ID, intro_style, heading_pattern)

로직:
1. 주제 카테고리 → 적합 포맷 후보군 매핑 (예: "적금/예금 비교" 주제는 `compare`, `guide` 후보)
2. 최근 N개(기본값 5) 발행 글에서 사용된 포맷 ID, intro_style을 확인
3. 후보군 중 최근 사용 빈도가 낮은 것을 우선 선택 (동일 포맷 연속 사용 최대 2회로 제한)
4. 선택 결과를 포함한 최종 프롬프트 변수 세트를 생성

출력: `{format_id, intro_style, heading_pattern, optional_blocks_selection}` → 이 값이 AI 생성 1회 호출의 시스템 프롬프트에 삽입됨

### 3.3 반복 회피 컨텍스트 주입 (Anti-Repetition Context)

AI 생성 호출 시, 아래 정보를 프롬프트에 함께 전달:
- 직전 3개 글의 제목
- 직전 3개 글의 소제목(H2/H3) 목록
- 직전 3개 글의 도입부 첫 문장

지시문 예시(프롬프트에 삽입될 지침, 실제 문구는 구현 시 확정):
> "아래 최근 발행 글들과 소제목 패턴, 도입부 화법이 겹치지 않도록 새 글을 작성하라. 표/체크리스트/가상 사례는 이번 포맷(`{format_id}`)에 필요한 것만 선택적으로 사용하라."

### 3.4 데이터 저장 요구사항

발행 글마다 아래 메타데이터를 저장해야 포맷 선택 로직(3.2)이 동작 가능:
- `format_id`
- `intro_style`
- `heading_pattern`
- `used_blocks` (실제 사용된 구성요소 목록)
- 발행일시

저장 위치는 기존 Publishing Engine 또는 Editor Engine의 글 메타데이터 스키마에 필드 추가하는 형태를 권장 (신규 테이블 생성 여부는 기존 스키마 확인 후 결정).

## 4. 구현 범위 제안 (단계적 접근)

Small Incremental Development 원칙에 따라 아래 순서 제안:

1. **1단계**: 포맷 프리셋 5종을 정적 데이터(JSON/설정 파일)로 정의만 하고, 아직 자동 선택 로직 없이 수동 지정 방식으로 프롬프트에 반영 → 실제 생성 결과 다양성 확인
2. **2단계**: 최근 N개 글 메타데이터 조회 + 포맷 선택 로직(3.2) 구현
3. **3단계**: 반복 회피 컨텍스트 주입(3.3) 추가
4. **4단계**: Quality Review AI 단계에서 "직전 글과의 구조 유사도"를 체크 항목으로 추가 검토 (기존 Quality Rules의 5개 지표에 추가할지는 별도 논의 필요)

---

## 5. 미결정 사항 (사용자 확인 필요)

- 포맷 프리셋 5종의 이름/개수가 적절한지, 실제 다루는 콘텐츠 주제(생활재테크 등)에 맞게 조정 필요 여부
- "최근 N개 글" 조회 시 카테고리 전체 기준인지, 같은 카테고리 내에서만 비교할지
- 4단계(Quality Review에 구조 유사도 체크 추가)를 이번 범위에 포함할지, 추후 별도 작업으로 분리할지

---

## 6. 이 문서의 용도

이 문서는 설계안이며 코드가 아닙니다. Claude Code에 전달 시:
1. 이 문서를 기반으로 기존 프로젝트 구조(Core/Prompt Engine 등 실제 코드베이스)와 맞춰 구체적 구현 계획을 다시 논의
2. 사용자 승인 후 1단계부터 순차 구현
3. 각 단계마다 기존 기능(Protect existing features 원칙)에 영향이 없는지 확인 후 진행
