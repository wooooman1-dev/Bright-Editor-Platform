# qualityTarget 판정 기준 분석

> 상태: 분석 기록 (구현 전)
> 대상: `core/content/ContentDepthPolicy.ts`, `core/content/LongFormDiagnostics.ts`
> 배경: 콘텐츠 포맷 다양화(`content-format-diversity-spec.md`) 착수 전 현행 판정 기준 검토

---

## 1. 결론 요약

완결성 원칙 자체는 타당하다. 다만 **섹션 유형을 제목 키워드로 추론하는 규칙**이 오분류를 만들고,
그 오분류가 본문 구조를 고정시켜 콘텐츠 다양성 문제의 직접 원인이 되고 있다.

---

## 2. 근거가 약한 것

### 2.1 섹션 유형을 제목 키워드로 결정 (`LongFormDiagnostics.ts:282`)

```ts
function inferSectionType(heading: string): ContentSectionType {
  if (/체크|목록|준비물/.test(heading)) return "checklist";
  if (/비교|차이|장단점/.test(heading)) return "comparison";
  if (/단계|순서|방법|실천/.test(heading)) return "steps";
  ...
}
```

제목에 포함된 단어가 그 섹션의 **필수 구조를 확정**한다. 순서 의존적이며 중복 매칭이 발생한다.

실제 사례 — `세전 세후 이자 비교는 예상 수령액으로 기록하기`
제목이 약속하는 역할은 **기록**이지만 "비교"가 포함되어 `comparison`으로 분류되고 표가 강제되었다.
한 문서의 H2 6개 중 3개가 "비교/차이"로 `comparison` 확정이었다.

한국어 재테크 제목에서 비교·방법·기준·순서는 사실상 회피 불가능한 어휘다.
`방법`은 `steps`로 분류되어 번호 리스트 3개를 요구한다.
**제목 어휘가 본문 구조를 지정하고, 어휘 분포가 도메인마다 고정되어 있으므로 본문이 매번 유사해진다.**

### 2.2 비교 판정 신호가 비교를 측정하지 않음 (`LongFormDiagnostics.ts:362`)

```ts
function comparisonSignals(text: string): number {
  return count(text, /비교|차이|장점|단점|반면|기준|선택|적합/g);
}
```

`기준`, `선택`, `적합`은 비교의 증거가 아니다. 일반적인 재테크 문장이면 표 없이도 3회를 쉽게 넘긴다.
결과적으로 이 게이트는 **분류에서 과민, 통과 판정에서 과관대**하다.

### 2.3 정보량 계산이 분량 지표에 가까움 (`LongFormDiagnostics.ts:238`)

```ts
informationElementCount = sentenceElements + listItemCount + tableCount * 3
sentenceElements = 12자 이상 문장의 개수
```

- 표는 행 수와 무관하게 일괄 3점
- 리스트 항목 1개 = 완결 문장 1개
- 12자 기준은 한국어로 대여섯 단어 수준

`comparison`의 최소 4점은 짧은 문장 4개로 충족된다.

### 2.4 깊이 분류가 거대한 문자열 위에서 동작 (`ContentDepthPolicy.ts:149`)

```ts
function classifyDepth(value: string) {
  if (/(?:비교|차이|vs\b|장단점|선택지|어떤 .* 좋|comparison)/i.test(value)) return "comparison";
```

`value`는 검색 의도, 콘텐츠 타입, 독자 문제, **projectStrategy 전체**, 도메인, 오디언스,
선택 주제를 이어붙인 문자열이다. 기획 실행부는 편집 컨텍스트 JSON 전체를 `projectStrategy`로 넘긴다.
따라서 그 JSON 어딘가에 "비교"가 한 번만 있으면 **모든 후보가 `comparison`으로 확정**된다.
주제별 판단이 아니라 사실상 프로젝트 단위 고정이다.

`ContentDepthPolicyInput`에는 `contentDepth` 필드가 없어, 기획서가 스스로 깊이를 선언할 수단도 없다.

## 3. 타당한 것

- **"섹션이 제목이 약속한 역할을 완결했는가"** 원칙 자체는 옳다. 실제 결함을 잡아낸 사례가 있다.
- **점수 제외 항목 분리** — imageStrategy, internalLinks, cta를 `not_evaluated`로 두어
  강제할 수 없는 것을 점수로 벌하지 않는다.
- **2단계 승인** — 표준 95 / 예외 90, 편집 항목만 상향하는 구조는 합리적이다.
- **`scopeBoundaries`와 근거 요구** — AdSense 승인 목표에 정확히 부합하며 실제로 작동한다.

---

## 4. 권고 (우선순위 순)

1. **섹션 유형을 기획서에서 가져온다.** 기획 단계가 이미 각 섹션의 역할을 알고 있다.
   제목 키워드는 폴백으로만 사용한다. 오분류 제거와 본문 다양화를 동시에 해결한다.
   계획된 역할과 실제 제목이 어긋나면 그것 자체를 진단으로 보고한다.
2. **`comparisonSignals`에서 `기준|선택|적합`을 제외**하고, 비교 대상이 2개 이상 식별되거나
   표가 있을 때만 통과시킨다.
3. **표 가중치를 내용 기준으로** 조정한다. 최소 2개 데이터 행 요구 또는 행 수 반영.
4. **`classifyDepth` 입력을 좁힌다.** 편집 컨텍스트 JSON 전체가 아니라
   검색 의도·주제·독자 문제만 전달한다. 아울러 기획서가 깊이를 선언할 수 있게 한다.

1번과 4번이 실질적 변화를 만들고, 2·3번은 판정 정확도 개선이다.

---

## 5. 포맷 프리셋에 대한 판단

스펙 3.1의 **프리셋 5종 고정은 권하지 않는다.**

- 5종을 순환하면 주기가 1에서 5로 늘어날 뿐 **더 긴 주기의 패턴**이 생긴다.
- 오해 바로잡기형·사례 중심형은 주제가 뒷받침해야 성립한다. 순번 때문에 적용하면
  없는 오해를 지어내야 하고, 이는 승인 정책의 근거 없는 주장 금지와 충돌한다.
- `qualityTarget`은 이미 연속적인 표현 공간을 갖고 있다. 5개 라벨로 접으면 정보가 줄어든다.
- 생활재테크에서 성립할 형태만 꼽아도 절차 안내·조건 판단·비교 선택·오해 정정·사례 적용·
  시기 안내·서류 안내로 7개 이상이며 도메인 특유다.

대안은 **열거 대신 제약**이다.

1. 발행된 글이 실제로 어떤 형태였는지 기록한다(기술적 기록, 사전 라벨 아님).
2. 다음 글에 "최근 N개와 형태가 겹치지 마라"는 제약만 건다.
3. 포맷 선택은 기획 AI가 주제 적합성에 따라 자유롭게 한다.

이 방식은 글이 쌓여도 제약이 유효하며 주기가 생기지 않는다.
`feat/editorial-diversity-context`가 이 구조의 절반을 이미 구현했다.
5종은 enum이 아니라 기획 프롬프트의 **열린 예시 목록**으로 쓰는 것이 적절하다.

---

## 6. 목적 축 분리 주의사항

현재 `qualityTarget` 도출은 `contentPurpose`를 알지 못한다.
`classifyDepth`, `sectionGuidance`, 승인 임계값 모두 승인용과 수익형에 동일하게 적용된다.

향후 수익형 콘텐츠를 다룰 때는 승인 단계 전제를 목적 구분 없는 공용 경로에 고정하지 않아야 한다.
승인용과 수익형이 같은 Core 아키텍처를 공유하되 판정 기준만 달라지는 구조를 유지한다.
