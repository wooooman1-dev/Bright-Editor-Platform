      으로 분류되는 진단 코드 부정확도 있음(검출 자체는 안 바뀜).
13. 건강보험 피부양자 재검사(위 10번으로 대상이 바뀜) 임무 중
    approval-readiness-designer 가 실측으로 승인 준비 게이트 버그 6건
    (P1~P6)을 찾아 전부 고쳤고, fix-verifier 3회 왕복(재작업 2회) 끝에
    커밋 `ad696d9 fix: repair approval readiness gate cache, persistence
    split, and version staleness` 로 통과했다.
    - P1 캐시가 순수 aggregate 재계산까지 건너뜀 → 항상 재도출하도록 수정.
    - P2 `content.quality` 와 `qualityReports[]` 두 사본이 서로 다른 값을
      가짐 → `reconcileApprovalReadinessAggregates` 로 통일해서 저장.
    - P3 옛 버전(approvalReadinessExecution.version) 판정이 자동
      무효화 안 됨 → 버전 불일치 시 스냅샷 기반 passed 만 needs_review 로
      강등.
    - P4 evidence 안내 문구가 실제 미확보 Claim 을 안 알려줌 →
      unverifiedFactFields/failureReason 반영.
    - P5 Standard Quality 미승인이면 나머지 5개 상태를 throw 로 은폐 →
      이제 각자 상태 유지하며 안내문만 추가(AGENTS.md 14장 상태분리
      원칙 때문에 "5개 전부 not_evaluated 로 덮으라"는 원 지시에서 의도적
      으로 벗어남 — fix-verifier 가 이 이탈이 오히려 옳다고 확인).
    - P6 `normalizeApprovalEvidenceCandidates` 가 매 버튼 클릭마다 검증
      상태를 초기화한 뒤 그걸 검증된 상태와 비교해 항상 "변경됨"으로
      오판 → 출처확인일이 매번 오늘 날짜로 재도장되고 출처 섹션이 벗겨짐.
      3차 재작업 끝에 `cited`/`selected`(provenance 파생값)까지 비교
      제외해서 citation/user_selected/document_link/system_verified
      4개 provenance 유형 전부에서 해결 확인.
    - **마이그레이션 영향(사용자에게 보일 수 있음)**:
      `approvalReadinessExecution.version !== "4.0"` 인 기존 콘텐츠는
      다음 저장 시 스냅샷 기반 passed 체크가 needs_review 로 강등되고,
      다음 실행 시 캐시 미스로 전체 재검사가 한 번 일어난다.
      `approval-live-msczog4z`, `content-mscjq0sq-xd8kp5` 가 정확히
      이 케이스 — 사용자 눈엔 "멀쩡하던 판정이 갑자기 여러 개
      needs_review 로 바뀜"으로 보일 수 있다. 한 번 재검사되면 이후
      캐시가 정상 히트한다.
    - 후속 과제(fix-verifier 지적, 커밋 차단 아님): identity 비교의 제외
      목록(`canonicalizerOwnedFields`) 상한을 고정하는 테스트가 없다 —
      URL 재정규화나 provenance 변경처럼 "여전히 재검증돼야 하는" 케이스를
      다음에 제외 목록을 넓힐 때 아무 테스트도 안 울린다. 다음 승인 관련
      작업 때 `tests/unit/app/application/approval/
      ApprovalReadinessAggregateIntegrity.test.ts` 에 그런 케이스를 1개씩
      추가할 것.
14. **진짜 미해결 제품 문제(게이트 버그 아님)**: `content-mscjq0sq-xd8kp5`
